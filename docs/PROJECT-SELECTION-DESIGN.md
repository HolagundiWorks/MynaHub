# Project creation and selection through the launcher (design)

**Status:** decided 2026-11-01 (section 6). Step 1 (wire and engine calls) is built; the launcher, O-CoreOp and O-Draft changes are not.
**Terms and links:** [SUITE.md](SUITE.md). **Data rules:** [PROJECT-HIERARCHY-AND-SECURITY.md](PROJECT-HIERARCHY-AND-SECURITY.md).

## 1. The decision

1. A project is created and chosen **only** in the launcher (or in O-Studio). O-CoreOp and O-Draft have no New project, Open project or Save As project.
2. After sign-in the launcher shows the company's projects in a drop-down. The user picks one and **locks** it.
3. Starting O-Draft or O-CoreOp from the launcher opens the locked project directly.
4. The launcher (and O-Studio) has a **basic wizard**: name, client, code, site address. Everything else (team, fees, stages, brief) is edited in O-Studio.

## 2. What exists today

| Piece | Where | State |
|---|---|---|
| Project record | company file, table `projects` (client, code, name, site address, status active/on_hold/completed, archived, `workspace_path`) | created in O-Studio only; O-CoreOp is refused by policy |
| Project folder | `office-core/src/project_workspace.rs`: `scaffold` makes a folder with `project.osp` named in `osas.project.json`; `attach_osp` copies an existing `.osp` in | the `.osp` itself is created when an app first saves |
| Active project | `active-project.json`, written by O-Draft, read by O-CoreOp | the apps decide, not the user |
| Project wizard | O-Draft `ProjectWizardWindow` (project details, team, floors and heights, layer sets, tabs, symbols), engine `project.wizard` | mixes project identity with drawing setup |
| New/Open project | O-Draft `project.setup`, `project.open`, File > Open/Save As `.osp`; O-CoreOp project settings and open/new | each app has its own |
| Start-up | launcher/O-Studio pass `OSTUDIO_COMPANY`, `OSTUDIO_TICKET`, `OSTUDIO_USER` | no project in the hand-off |

The company file already has the right model (a project owns a workspace folder with one `.osp`). The change is **who chooses**, not where data lives.

## 3. Target flow

**Wording and states (2026-11-01).** The launcher says *Load project* and *Close project* (not lock and unlock; the wire and files keep the name "locked project"). With no project loaded the list and its search are active, *Load project* and *New project…* are active and *Close project* is not. With a project loaded the list, search, *Load project* and *New project…* are inactive and *Close project* is active; it is refused, naming the app, while O-CoreOp or O-Draft is open. Closing the project makes the list active again.


```
Launcher: sign in -> drop-down of projects (search, recent first)
        -> [New project...]  basic wizard (name, client, code, address) -> workspace + project.osp created now
        -> pick one -> [Lock]   (selection saved in suite.json)
Start O-Draft / O-CoreOp -> env OSTUDIO_PROJECT_ID + path -> app opens that project.osp, title shows "Project name"
Change project -> only in the launcher, refused while an app holds the project (shows which)
```

### 3.1 Wire changes

The lock is a file of its own, `%LOCALAPPDATA%\O-Studio\selected-project.json` (not a block in `suite.json`, which the company login rewrites whole and would drop it):

```json
{ "format": "studio-selected-project", "version": 1, "company": "D:\\Practice\\Acme.osas",
  "project": { "id": 17, "code": "P-2026-017", "name": "Rao Residence", "osp": "D:\\Practice\\projects\\p17\\project.osp" },
  "locked_by": "anita", "locked_utc": "2026-11-01T06:10:00Z" }
```

A selection made for another company reads as none. Code: `Osas.Core.SelectedProjectStore`.

Apps are started with `OSTUDIO_PROJECT_ID` and `OSTUDIO_PROJECT_OSP` beside the existing variables. The active-project pointer stays for one release (O-CoreOp's live notice) and is then retired. Constants go in `Office.Shared.SuiteWire`, `Osas.Core.SuiteWire` and `aad-office::wire` (the three copies already kept equal).

An app **verifies** what it is given: the project exists in the company file, is not archived, and the path is the recorded workspace path. It never trusts the path alone.

### 3.2 Basic wizard

Fields: client (pick or add), project name, code (generated by `project_codes`, editable), site address. It calls the same office-core function O-Studio uses to create a project and then `scaffold`, so launcher and O-Studio cannot diverge. It needs the **Edit** permission; an Auditor sees the list and cannot create. The workspace folder is made at once. The `.osp` itself is made by the app that first opens the project (O-Draft and O-CoreOp already create a missing project file), so an app opening a locked project whose file is absent creates it rather than failing.

O-Draft's current wizard splits in two: project identity moves to the launcher; **drawing setup** (floors and heights, layer sets, discipline tabs, symbols) stays in O-Draft as "Drawing setup", offered automatically the first time an empty project opens.

2. Launcher: drop-down, lock, wizard, `suite.json`.
3. O-CoreOp then O-Draft read the lock; keep the old UI behind a development switch.
4. Remove the old project UI; update docs and plans; run the suite test program on the new build.

## 5. Issues to expect

**Data and files**
1. **Existing projects.** Users have standalone `.osp` files and recent lists. They need "Add to company" (use `attach_osp`) or they vanish from view. Provide an import in the launcher.
2. **Workspace paths are per machine.** `projects.workspace_path` is an absolute path in the company file. A second PC, a moved folder, or a drive letter change breaks it. Store a path relative to the company file's folder, with a per-machine override, and show "folder not found, locate it".
3. **Project exists only in the cloud.** A project created on another PC has a record but no local `.osp`. The drop-down must show it as "not downloaded" and pull through O-Studio's Neon sync before the apps start.
4. **Two machines, one project.** Revisions conflict at sync, not at lock. The lock is local; it must not be mistaken for a team lock. Say so in the UI.
5. **O-Draft holds many drawings.** A project has several drawings, but Draft has tabs, xrefs and underlays that are files outside the project. Decide whether external DWG/DXF open as "import into project" (changes stored copies) or as a temporary external tab. Xref paths relative to the old location need a rule.
6. **Levels and floors have two owners.** O-CoreOp project levels and O-Draft's wizard floors describe the same building. One of them must become the source (proposal: the `.osp` project record, edited in Draft's drawing setup, read-only in CoreOp).

**Behaviour**
7. **Switching while apps run.** Recommended: refuse and name the app. Allowing it would leave an app writing to a project the user thinks is closed.
8. **Archived, on-hold and completed projects.** Show them, open completed ones read-only, and refuse archived ones.
9. **Roles.** Auditor and read-only roles open the project read-only; the apps must honour that from the ticket role, not only hide buttons.
10. **Starting an app directly (Start menu, file association).** With no lock and no sign-in, the app has nothing to open. Either it starts the launcher and waits (the requirement from earlier today) or shows a "use the launcher" screen. The first is the proposal; it also removes the "work without a company" mode that INT-LNC-04 tests.
11. **Quick look at a plain DXF.** Some users open a drawing from a client with no project. Without a "temporary drawing" mode this is impossible. Keep a clearly labelled **Scratch** project per user, created on first use, so the rule "everything lives in a project" holds.
12. **Persona and first-run details.** CoreOp needs a persona (Project Manager/PMC or Contractor) and rate book for a new project. The launcher wizard does not ask; CoreOp must open its project settings once, or Studio's project page supplies them.

**Technical**
13. **The launcher keeps the company file open.** Its shared claim blocks operations that need exclusive access, for example protecting the file (O-Studio releases its own claim for that). The launcher must release the claim on request or reopen briefly for each call.
14. **The ticket is single-use and 120 seconds.** Project selection does not belong in it; it goes in env/`suite.json`. A stale `suite.json` (project deleted or archived since) must fail clearly.
15. **Tests that open arbitrary files** (control channel `app.open`, the CLI, mutation tests) must keep working, so the restriction applies to the interactive UI only.
16. **Large lists.** A practice may have hundreds of projects. The drop-down needs search and grouping by client, not a plain list.
17. **Path injection.** An environment variable holding a path is a trust boundary (section 3.1): verify against the company file.
18. **Permissions already differ by app.** O-CoreOp is refused project creation by policy (`CompanyOfficePolicy`); the launcher is the first non-Studio place to create projects, so the policy needs a launcher entry rather than being loosened for CoreOp.

## 6. Decisions (2026-11-01)

1. **No scratch project.** Quick viewing of a plain DXF is not supported; a drawing is always inside a project. (Issue 11 becomes: DXF/DWG are imported into the project only.)
2. **Drawing setup stays in O-Draft** (floors and heights, layer sets, discipline tabs, symbols), offered when an empty project first opens.
3. **An app started with no lock** starts the launcher and waits; it never works without a company and project.
4. **Switching projects while an app has the current one open is refused**, and the launcher names the app.
